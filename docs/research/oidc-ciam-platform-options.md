# OIDC and CIAM platform options for Tripper

Research date: 2026-09-20

## Question and constraints

Which managed or self-hosted identity platform, if any, should Tripper use for these two milestones?

- Private browser pilot: a small known group, all of whom may be required to use Google.
- Public release: browser plus React Native mobile, with Google, Apple, and passwordless email; users may explicitly link multiple identities, but Tripper must never merge accounts merely because email addresses match.
- Authentication establishes which Tripper Account is present. Trip roles and all Creator/Contributor/Traveller authorization remain current-state application data in PostgreSQL, not identity-provider claims.

This is a first-party-source comparison. Prices are public list prices observed on the research date and must be rechecked before purchase.

## Conclusion

Keep direct Google OpenID Connect for the private browser pilot. It is already a standards-based authentication integration, not a temporary Basic Auth scheme: Google documents its implementation as OpenID Certified and provides discovery, authorization, token, user-info, and public-key endpoints. The pilot gains no material benefit from putting a broker in front of its sole identity provider ([Google OIDC documentation](https://developers.google.com/identity/openid-connect/openid-connect)).

For the public web-and-mobile release, introduce a CIAM/OIDC broker if the stated three-method and explicit-linking requirements remain. Direct integrations are technically possible, but they make Tripper itself the identity orchestration product: it must implement Apple and Google lifecycle differences, passwordless-email delivery and abuse controls, safe linking and unlinking with fresh authentication, recovery, MFA/passkey evolution, mobile redirects, token/session hardening, and an identity administration surface. Apple also requires an equivalent privacy-preserving login option in many apps that use Google or another social login for the primary account ([App Review Guideline 4.8](https://developer.apple.com/app-store/review/guidelines/uk/)).

The managed shortlist is:

1. **Auth0 Essentials - best fit when minimizing implementation and security work is the priority.** It meets the required methods, native/mobile flow, explicit account linking, standards boundary, custom domain, EU data locality, and future MFA/passkeys. Its material drawback is pricing: manual account linking is not in Free, so Tripper needs at least Essentials, currently **$35/month for 500 MAU**.
2. **Amazon Cognito Essentials - best fit when minimizing cash cost is the priority and AWS-specific engineering is acceptable.** It has a permanent 10,000-MAU free tier for direct/social users, then a published $0.015/MAU example rate, and includes email passwordless and passkeys. Its account-linking primitive is an administrator API that must run before the new federated identity's first sign-in; building safe user-initiated linking is therefore appreciably more custom and fragile than Auth0.

The self-hosted shortlist is **SuperTokens** and **ZITADEL**, but neither beats Auth0 on Tripper's stated goal of simplicity. SuperTokens meets the method and manual-linking requirements, but linking is a licensed paid feature with a public $100/month minimum and its normal integration is product-specific rather than using Tripper purely as a standard OIDC relying party. ZITADEL is standards-first and supports managed-to-self-hosted portability, but its hosted login currently lists email OTP as MFA while listing only passkeys as passwordless; passwordless email as a primary method would require a custom login using the Session API. **Keycloak is not shortlisted for implementation** because its official distribution has excellent OIDC, brokering, linking, MFA and passkeys, but not an out-of-the-box Apple provider or primary email magic-link/OTP method; extensions plus production operations defeat the simplicity objective.

If selecting today, choose **Auth0 Essentials for the public release**, conditional on a small proof that exercises Google, native Sign in with Apple, email OTP (prefer OTP over a same-device magic link), and reauthentication-backed explicit linking. Choose Cognito instead only if its lower recurring cost is worth owning a custom linking flow and the team wants AWS as the operational center of gravity.

Do not migrate Trip authorization into any provider. Store a stable local `Account` and application-owned `ExternalIdentity(provider_issuer, provider_subject)` rows; resolve a validated external identity to an Account, then load trip membership and role from PostgreSQL on every protected request. This also contains vendor lock-in and permits an identity-provider replacement without changing trip ownership or authorization data.

## Options screened out

- **Clerk** has strong Expo/native support, passwordless email and passkeys, but its documented OAuth behavior automatically attempts to link an OAuth identity to any existing Clerk account with the same email. That directly conflicts with Tripper's no-email-auto-link rule ([Clerk account linking](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking)).
- **Supabase Auth** supports Google, Apple, passwordless methods and React Native, plus manual linking, but it also automatically links a new OAuth identity to an existing user with the same email; manual linking is marked beta in the current documentation ([Supabase identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking), [React Native](https://supabase.com/docs/guides/auth/quickstarts/react-native)). This is unsuitable unless Supabase adds a supported configuration that fully disables email-based auto-linking.

These are policy exclusions, not judgments about general product quality.

## Migration and lock-in controls

Regardless of the public provider:

1. Keep Tripper's `Account.id` provider-neutral. Store `(issuer, subject)` as the external identity key; never use email as identity or linking evidence.
2. Make linking an authenticated account operation. Require a recent Tripper session and fresh authentication of the identity being added; surface conflicts for deliberate recovery/support handling.
3. Keep session creation and account resolution behind a small adapter. Web can continue to use an opaque `HttpOnly`, `Secure`, `SameSite` Tripper cookie; React Native can use Authorization Code + PKCE and send a short-lived access token to the API. The identity platform need not know Trip roles.
4. Export provider configuration and user/identity mappings periodically where supported. Do not store any role or trip membership only in provider metadata or claims.
5. Because pilot access may be discarded, public cutover can create new Accounts. There is no reason to introduce a broker during the pilot solely for migration.

## Proof required before committing to Auth0

A time-boxed proof should verify only risks not settled by documentation:

- one browser and one React Native client use the same Auth0 tenant and resolve to the same local Account;
- native Sign in with Apple and Google work with production-style client IDs and callback/custom-domain configuration;
- email OTP works on mobile without depending on opening a magic link in the initiating browser;
- an already authenticated user can explicitly link a second provider after fresh authentication, while an unauthenticated same-email sign-in does **not** merge accounts;
- unlinking cannot remove the last usable identity without an explicit recovery path;
- Auth0 subject/identity exports contain enough data to rebuild Tripper's `ExternalIdentity` mappings.

No provider proof should put Trip roles in identity claims; authorization remains a Tripper concern.
